# 四种应用层协议实现共性分析报告

## 1. 背景与目的

`protocol-example` 已包含 CoAP、MQTT、SMTP、FTP 四种应用层协议的基础实现，并具备代码、构建脚本和最小可运行路径。  
这份报告不复述协议知识，而是从现有样例中总结一条更适合 agent 使用的分析路径：当 agent 面对一份协议文档时，首先要识别它在工程上究竟要求哪些模块、哪些状态、哪些约束，而不是直接把 RFC 内容平铺成代码任务。

从当前四个样例看，协议实现并不是“把命令一个个写出来”这么简单，而是要先建立一个稳定骨架：网络适配、协议解析、状态保存、路由分发、业务处理、错误与限制、构建与验证。  
因此，本报告的目标是提炼四种协议在实现层面的共性，并把这些共性转化为后续 agent 制定实施计划时可复用的约束模板。

## 2. 四类协议样例的实现视角

| 协议 | 传输方式 | 核心交互模型 | 主要状态对象 | 典型处理目标 |
| --- | --- | --- | --- | --- |
| CoAP | UDP | 请求/响应 | 资源状态、请求上下文 | 资源访问与响应生成 |
| MQTT | TCP 长连接 | 发布/订阅 | session、topic 订阅关系 | 消息路由与转发 |
| SMTP | TCP | 命令/响应 | 会话状态、认证状态、邮件事务 | 接收邮件并落盘 |
| FTP | TCP 控制连接 + 数据连接 | 命令/响应 + 文件传输 | 会话状态、认证状态、PASV 状态 | 文件系统访问与传输 |

如果从目录结构看，这四个样例已经体现出一种稳定模式。CoAP 主要落在 `network/protocol/resource/server`，MQTT 落在 `network/protocol/broker/router/topic`，SMTP 落在 `network/protocol/server/auth/storage`，FTP 落在 `network/protocol/server/auth/resource`。  
也就是说，不同协议虽然业务目标不同，但代码分层非常接近：先把网络与协议语义拆开，再把状态和业务处理拆开，最后由一个中心入口统一调度。

## 3. 共性实现特征

- 传输层适配是第一步。实现前必须明确协议依赖 UDP 还是 TCP，是否有连接对象，是否需要读缓冲、写队列、事件循环，以及是否存在单独的数据通道。CoAP 的网络层较薄，而 MQTT、SMTP、FTP 都需要更明确的连接生命周期。
- 协议编解码是第二步。四个样例都把“原始输入”转换成“结构化对象”后再处理。CoAP 和 MQTT 更偏二进制报文解析，SMTP 和 FTP 更偏命令行解析，但本质都是先解码、再校验、再分发、最后编码响应。
- 状态管理是实现能否稳定扩展的关键。MQTT 的 session 保存连接、client_id、keepalive；SMTP 要保存问候、认证状态、收件人和 DATA 事务；FTP 要保存认证状态、当前目录和 PASV 状态；CoAP 虽然无连接，但仍然有资源状态和请求上下文。可见“是否需要状态对象”不是可选项，只是粒度不同。
- 路由与分发机制普遍存在。CoAP 通过 URI 和方法分发到资源处理器；MQTT 通过 packet type、topic 和 router 分发；SMTP/FTP 通过命令名驱动处理逻辑。说明协议实现一般都需要一个显式的 dispatch 层，而不是把所有逻辑塞进网络回调里。
- 业务对象需要被单独抽象。当前样例中已经出现了典型对象：CoAP resource、MQTT topic/subscription、SMTP mail、FTP file/dir。这些对象一旦明确，后续模块边界和测试样例也就基本确定了。
- 安全边界与限制必须内建在实现中。SMTP 有最大收件人和消息大小限制，FTP 有根目录沙箱与路径规范化，MQTT 对已支持报文范围做裁剪，CoAP 也只覆盖常见选项和基础响应。可见最小实现并不意味着“少做校验”，反而意味着必须明确实现边界。
- 构建与验证闭环属于实现的一部分。四个样例都配有 `Makefile`、`README` 和最小测试路径，说明一个可用的协议实现不仅是源码集合，还包括构建入口、运行方式和可复现验证方法。

## 4. 关键差异与对实现方案的影响

agent 不能只抓共性，还必须尽早识别差异，因为差异决定计划的主轴。  
第一，有连接与无连接会直接决定是否需要 session、缓冲区、连接关闭处理和长生命周期状态。第二，单通道与控制/数据双通道会显著改变网络层设计，FTP 因为 PASV 数据连接而天然更复杂。第三，资源导向、命令导向和消息导向决定了分发机制的核心索引分别是 URI、命令名还是 topic。第四，是否存在本地存储、目录沙箱、订阅树、消息路由树等特定抽象，会直接决定业务层的单独模块。第五，是否存在显式状态机和多阶段事务，会决定是否需要把认证、事务和中间状态从处理函数中分离出来，形成独立的状态对象。

这些差异说明，agent 在制定计划时不能只输出一份统一目录模板，而必须先判断该协议更像“资源服务”“命令会话”“消息中枢”还是“控制+数据协同”的混合体，然后再决定模块拆分方式。

## 5. 对 agent 制定协议实施计划的约束

为了让 agent 生成的计划更稳定，实施计划中至少必须包含以下内容：

- 传输层与运行模型：UDP/TCP、阻塞或事件驱动、单连接还是多连接、是否有额外数据通道。
- 报文模型与编解码范围：输入如何切分、报文或命令如何表示、哪些字段必须支持、哪些高级特性暂不实现。
- 状态对象设计：哪些状态属于连接级、事务级、认证级、资源级，状态何时创建、更新和释放。
- 路由/调度设计：按什么键分发，调度中心放在哪一层，哪些逻辑应进入 router、handler 或 server。
- 安全与边界限制：长度上限、路径/主题合法性、未认证行为、异常输入处理、实现范围裁剪。
- 存储或资源抽象：是否需要文件系统、消息树、资源表、邮件存储、键值表等持久或半持久对象。
- 最小可运行功能集：必须先定义 v1 覆盖哪些命令、报文、资源或事务路径，避免一开始就追求全协议。
- 测试与验证方式：如何编译、如何启动、最小交互样例是什么、预期输出是什么。

更关键的约束是，agent 必须先从文档中抽取四类核心语义，再细化工程模块：

- 协议交互模型：请求/响应、命令/响应、发布/订阅，还是控制/数据双通道。
- 状态粒度：协议是否需要 session、事务状态机、认证阶段或资源状态。
- 资源对象：系统真正操作的对象是什么，是 topic、资源、邮件还是文件。
- 错误语义：遇到非法输入、未授权、资源不存在、长度越界、未支持功能时该如何响应。

只有这四类语义先被抽取出来，后续的目录、文件、接口和测试计划才不会失焦。否则 agent 很容易生成一份“模块名看起来合理，但实现顺序和边界都不稳定”的计划。

## 6. 结论

这四类应用层协议虽然在语义上分别面向资源访问、消息分发、邮件接收和文件传输，但从工程实现角度看，都可以收敛为六类核心问题：网络适配、协议解析、状态管理、分发处理、边界控制和验证。  
因此，后续 agent 面对新的应用层协议时，可以先按这六类问题建立实现骨架，再根据该协议的交互模型、状态复杂度和业务对象做差异化展开。  
这种方式的价值在于，它既保留了实现计划的约束性，又避免 agent 一开始就陷入零散的 RFC 细节，能够更稳定地从文档走到工程方案。
