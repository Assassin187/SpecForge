## 4. Step 1 进度：Artifact Boundary Audit

```text
Status: Completed
Started At: 2026-06-12
Completed At: 2026-06-12 10:20 CST
```

### 目标

盘点当前 specs 字段、生产者、消费者和 artifact boundary，判断哪些字段属于：

- coder-facing strict specs；
- planning internal IR；
- sidecar；
- validator-only artifacts；
- 当前边界不清或风险较高的字段。

### 应检查路径

```text

agent/coder/specs.py
agent/coder/models.py

agent/coder/header_recipes.py

agent/planning/stages/specs_compiler.py
agent/planning/validators/
agent/planning/out/
```

### 预期输出

```text
docs/specs_optimization/01_artifact_boundary_audit.md
```

### 完成记录

```text
Completed Work:
- 静态审查三类 strict specs schema、planning compiler/lowering、coder loader/models、header renderer、source/repair prompts 和 validators。
- 建立字段级 producer/consumer 矩阵，区分 loader、header、source prompt、repair prompt、schema validation 和 semantic validation 消费。
- 审查完整 planning 输出样例、sidecars、dependency graph、validation reports 和已有 coder compile failure 日志。
- 明确 strict specs、planning internal IR、pure sidecar、validator-sidecar 和 validator-only artifact 边界。

Artifacts:
- `docs/specs_optimization/01_artifact_boundary_audit.md`
- `docs/任务进度.md`

Key Findings:
- `PUBLIC_SYMBOLS`、`ACCESS_PATHS`、`CALL_CONTRACTS`、`FORBIDDEN_SYMBOLS`、`WIRE_MAPPING`、`TEST_VECTORS` 等字段通过 `raw` 被 prompt 或 validator 隐式消费，不能仅依据 coder dataclass 判断其可删除性。
- compiler 当前从同一 `imports_allowed` 同时生成 `SOURCE.DEPENDENCY` 和 `HEADER.DEPENDENCY`，未区分 source call dependency 与 public header/type dependency，也未生成 `HEADER.SYSTEM_DEPENDENCY`。
- deterministic dependency fallback 会清空 `calls_allowed` 和 `imports_allowed`；已有样例中 `call_contracts` 非空但 function edges/imports 为空，dependency validation 仍 passed。
- planning coder compatibility validation 使用 `validate_rendered_headers=False`，无法拦截已有 `ssize_t` missing system include 等 deterministic header compile failure。
- `planning_decisions.json` 和 `planning_ir_refs.json` 是 validator-sidecars；`planning_traceability.json` 当前是 pure sidecar。
- `DOC_REF`、`PROTOCOL.SCOPE`、部分 nested `ROLE`、function `PUBLIC_SYMBOLS` 是优先 sidecar/omit 候选；`SOURCE.DATA`、structured signature/contract 等字段更可能需要强化 consumer，而不是直接移出 strict specs。

Blockers:
- 无。Step 1 静态审计已完成；未运行 Step 2 工具或大规模实验。

Next Step Recommendation:
- Step 2 优先支持 dependency/header/type closure diff 与 fail-closed diagnostics，其次支持 `calls_allowed`、`call_contracts`、`imports_allowed`、`signature_dependencies` 的跨层一致性检查。
- Step 2 不得通过清空 dependency 字段、删除所有 dependency edges 或降低 coder compatibility validation 强度制造通过结果。
```

```text
Completed Work:
- 使用 Step 2 的 `degrade_specs.py` 为 MQTT、CoAP 生成 7 组 gold degradation profiles。
- 对 14 个 protocol/profile 组合完成 schema validation、coder loader validation 和 rendered header validation。
- 对 14 个 protocol/profile 组合完成 bounded coder generation、compile、repair 和 smoke behavior verification。
- 汇总 spec load、rendered header、compile、repair iterations、smoke、LoC、compile error、missing symbol/type、dependency/header error 和 hallucinated symbol metrics。

Artifacts:
- `experiments/specs_optimization/gold_degradation/`
- `experiments/specs_optimization/gold_degradation/results.json`
- `experiments/specs_optimization/gold_degradation/results.md`
- `docs/specs_optimization/03_gold_degradation_evaluation.md`
- `docs/任务进度.md`

Key Findings:
- MQTT、CoAP `Gold-Full` 当前仍可通过完整 coder run；MQTT 需 1 轮 source repair 后 compile 通过且 4/4 smoke pass，CoAP initial compile 通过且 4/4 smoke pass。
- 全部 degradation profiles 均通过 schema、spec load 和 rendered header validation；删除 behavior/wire/calls/test vectors 后最先出现的问题在 generated source compile 或 smoke behavior 层，不在 loader/header 层。
- `Gold-Sidecar-Only-Traceability` 在 MQTT、CoAP 均 compile + smoke 通过，支持 module/file `DOC_REF` 更适合 sidecar，而非 strict coder specs 硬必需字段。
- `Gold-No-Wire-Binding` 在 MQTT、CoAP 均 compile + smoke 通过；在保留 `ACCESS_PATHS` 的前提下，function-level `WIRE_MAPPING` 未显示为当前 coder 硬必需字段。
- `Gold-No-Behavior-Detail` 导致 MQTT source compile failure，并导致 CoAP smoke degradation；behavior detail 对 source generation 与 protocol behavior 仍有实际价值。
- `Gold-No-TestVectors` 在 MQTT 通过，但 CoAP compile 后 0/4 smoke pass，说明 test vectors 至少对部分协议的 behavior anchoring 有价值。
- `Gold-No-Calls` 不阻断 compile，但 MQTT mosquitto interop timeout，CoAP 需 1 轮 repair，说明 calls/rely 信息更像质量和 interop guard，而非 loader/header 硬字段。

Blockers:
- 无输入缺失、无 API/timeout blocker、无 Step 2 工具 bug 修复。
- 每个 profile 只做单次 LLM generation，结果受 nondeterminism 影响；需要 Step 4 或 repeated runs 验证稳定性。

Next Step Recommendation:
- Step 4 - Planning-vs-Gold + Oracle Diagnosis
```
