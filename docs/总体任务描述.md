# 总体任务描述.md：SpecForge Specs 结构与生成阶段优化验证

## 1. 大任务目标

本任务的目标是验证当前 SpecForge 是否需要对 specs 本身结构进行优化和修改，并进一步判断：

1. 当前 coder-facing specs 是否过细、过重；
2. 哪些 specs 字段对 coder 是必需的；
3. 哪些字段应保留在 planning internal IR 或 sidecar，而不是 strict coder specs；
4. planning 当前无法产出高质量 specs 的主要瓶颈位于哪些 stages；
5. 后续应该优先优化 specs schema、specs compiler、dependency lowering、validator，还是某些 LLM planning substages。

本任务不是直接进行大规模重构，而是先建立证据，再决定是否修改 specs 结构。

---

## 2. 背景

已知事实：

- MQTT、CoAP 的 example specs 可以驱动 coder 生成符合协议行为的代码。
- example specs 来自真实可验证代码，因此说明 coder 主流程基本可用。
- planning 自动生成的 specs 输入 coder 后出现依赖/header 相关失败。
- 本次失败更可能暴露 specs compiler、dependency lowering、public type dependency、system type registry 和 final coder compatibility validation 的问题，而不能直接证明 specs 结构过重。

已知错误根因包括：

1. dependency fallback 删除全部依赖，使 dependency graph 因为无边而假通过；
2. header 与 source dependency 被错误合并；
3. public type dependency 没有完整参与 header dependency lowering；
4. system type lowering 不完整；
5. final compatibility validation 跳过 rendered header validation。

---

## 3. 总体判断思路

不要直接问“当前 specs 是否太细”。应通过实验回答：

```text
如果删减 example specs 的某些字段后 coder 仍能稳定成功，
则这些字段可能不应进入 coder-facing strict specs。

如果删减这些字段后 coder 成功率明显下降，
则这些字段对 coder 是必要信息，问题更可能在 planning 生成质量或 lowering/validator。

如果 planning 输出的语义覆盖接近 example specs，
但失败集中在 header/dependency/system type，
则应优先修 compiler/validator，而不是简化 specs。

如果 planning 输出在 function family、wire binding、behavior contract 上明显不足，
则应优化对应 planning substages。
```

# Step 1：Artifact Boundary Audit

## 目标

确认当前 specs 的字段边界和消费关系，判断哪些字段属于：

1. coder-facing strict specs；
2. planning internal IR；
3. sidecar；
4. validator-only artifacts；
5. 当前混入位置不合理的字段。

本步骤只做静态分析，不运行大规模实验，不修改核心 pipeline。

## 主要问题

需要回答：

- 当前 `PROTOCOL_MODULE_SPEC`、`FILE_SPEC`、`FUNCTION_SPEC` 中有哪些字段？
- 哪些字段被 coder loader 消费？
- 哪些字段被 header renderer 消费？
- 哪些字段被 source generation prompt 消费？
- 哪些字段只用于 validation 或 traceability？
- 哪些字段可能应该移入 sidecar？
- 哪些字段与本次 dependency/header 失败直接相关？

## 建议检查对象

根据仓库实际路径调整，优先检查：

```text
specs-example/
agent/coder/specs.py
agent/coder/models.py
agent/coder/generation.py
agent/coder/header_recipes.py
agent/coder/prompts.py
agent/planning/stages/specs_compiler.py
agent/planning/validators/
agent/planning/out/
```

## 输出产物

建议输出：

```text
docs/specs_optimization/01_artifact_boundary_audit.md
```

报告至少包含：

```text
1. 当前 strict specs 字段清单
2. 字段生产者与消费者映射
3. strict specs / sidecar / validator-only 的建议边界
4. dependency/header 相关字段的风险点
5. 下一步实验需要重点验证的字段
```

必须包含字段级表格：

```text
| field/category | current producer | current consumer | coder required? | validator required? | can move to sidecar? | risk if removed | evidence path |
```

## 完成标准

- 能清楚说明哪些字段是 coder 真正消费的；
- 能指出至少 3 类可能边界不清的字段；
- 能明确下一步 degradation 实验应优先删减/弱化哪些字段；
- 已更新 `任务进度.md`。

# Step 2：Diagnostic Toolkit Construction

## 目标

构建最小诊断工具集，为后续 Step 3 和 Step 4 提供可复用工具。

本步骤可以写脚本，但不要求完成全部实验运行。

## 工具范围

为了控制单轮工作量，只要求实现或设计以下最小工具：

### Tool A：Gold Specs Degradation Generator

输入 example specs，输出若干降级版本 specs。

至少支持以下 profiles：

```text
full
no_behavior_detail
no_wire_binding
no_calls
min_interface
no_test_vectors
sidecar_only_traceability
```

如果某些字段在当前 schema 中不存在，应在报告中说明并跳过。

### Tool B：Spec Field Consumer / Diff Tool

比较 example specs 与 planning specs，输出字段覆盖差异。

至少统计：

```text
module coverage
file coverage
function count and family coverage
public type coverage
signature coverage
behavior field presence
wire/access field presence
calls/dependency presence
test vector presence
```

### Tool C：Oracle Substitution Skeleton

提供 oracle substitution 的最小框架或设计，不要求实现所有替换策略。

优先支持：

```text
P+GoldDependency
P+GoldType
P+GoldSignature
```

如果一次实现三个替换过重，则先实现 skeleton 和 P+GoldDependency。

## 建议路径

```text
tools/specs_optimization/
  degrade_specs.py
  compare_specs.py
  oracle_substitute.py
  README.md
```

## 输出产物

```text
docs/specs_optimization/02_diagnostic_toolkit.md
tools/specs_optimization/*
```

报告至少包含：

```text
1. 工具入口和使用方式
2. 支持的 degradation profiles
3. 支持的 diff metrics
4. 已实现与未实现的 oracle substitution
5. 已知限制
```

## 完成标准

- 工具能对 example specs 目录运行，至少生成降级 specs；
- diff 工具能输出 markdown 或 json summary；
- oracle 工具至少有清晰 skeleton，不阻塞后续手工替换；
- 已更新 `任务进度.md`。

# Step 3：Gold Specs Degradation Evaluation

## 目标

使用 Step 2 的工具对 MQTT、CoAP example specs 做降级实验，判断哪些 specs 字段对 coder 是必要的。

本步骤优先运行低成本验证。如果 coder 运行需要 LLM 或外部 API，可先完成：

1. spec load validation；
2. rendered header validation；
3. static schema validation；
4. 如条件允许，再运行 coder compile/smoke。

## 实验配置

至少对 MQTT 和 CoAP 执行以下 profiles：

```text
Gold-Full
Gold-No-Behavior-Detail
Gold-No-Wire-Binding
Gold-No-Calls
Gold-Min-Interface
Gold-No-TestVectors
Gold-Sidecar-Only-Traceability
```

如果某个 profile 无法构造，应记录原因。

## 指标

至少记录：

```text
spec load success
schema validation success
rendered header success
compile success if available
repair iterations if available
smoke test success if available
missing type/symbol count
dependency/header error count
behavior-related warning count
```

## 输出产物

```text
docs/specs_optimization/03_gold_degradation_evaluation.md
experiments/specs_optimization/gold_degradation/
```

报告必须包含：

```text
| protocol | profile | spec_load | header_validation | compile | smoke | key_errors | interpretation |
```

## 完成标准

- 至少完成 MQTT、CoAP 的 specs 降级版本生成；
- 至少完成 schema/spec load/header 层面的验证；
- 能初步判断哪些字段不能轻易删除；
- 能初步判断 strict specs 是否可能过重；
- 已更新 `任务进度.md`。

# Step 4：Planning-vs-Gold + Oracle Diagnosis

## 目标

定位 planning 自动生成 specs 与 example specs 的差距，并通过有限 oracle substitution 判断主要瓶颈阶段。

本步骤将两个原本独立的任务合并：

1. Planning-vs-Gold Diff；
2. Oracle Stage Substitution。

合并原因：二者都依赖 Step 2 的 diff/substitution 工具，且都服务于 stage-level diagnosis。

## 输入

至少需要：

```text
1. MQTT example specs
2. CoAP example specs
3. 至少一个 planning 自动生成的 MQTT spec_bundle
4. 如有条件，加入 planning 自动生成的 CoAP spec_bundle
5. coder 失败日志或 validation report
```

如果当前仓库没有 CoAP planning 输出，只对 MQTT 做完整分析，并记录缺失。

## Planning-vs-Gold Diff 维度

至少分析：

```text
module coverage
function family coverage
public type closure
signature completeness
behavior contract actionability
wire/access binding coverage
calls_allowed precision
file layout consistency
header/source dependency separation
system type lowering
coder compatibility validation gap
```

## Oracle Substitution 优先级

为了控制工作量，只要求优先做 3 个：

```text
P+GoldDependency
P+GoldType
P+GoldSignature
```

如果时间允许，再补充：

```text
P+GoldBehavior
P+GoldWire
P+GoldCalls
```

## Stage 映射

将发现的问题映射到 planning stages：

```text
5.3_type_data
5.4a_function_inventory
5.4b_function_signatures
5.4c_function_behavior_contract
5.4d_wire_access_binding
5.4e_call_contracts
5.5a_file_layout
5.5b_runtime_entrypoint
5.6_dependency_closure
5.7_spec_readiness
specs_compiler
coder_compat validator
```

## 输出产物

```text
docs/specs_optimization/04_planning_vs_gold_oracle_diagnosis.md
experiments/specs_optimization/oracle_substitution/
```

报告必须包含：

```text
1. Planning-vs-Gold 差异总结
2. Oracle substitution 运行结果或静态替换结果
3. stage-level diagnosis matrix
4. 当前最可能瓶颈排序
```

必须包含矩阵：

```text
| symptom | likely stage | evidence | validator gap | possible fix | risk |
```

## 完成标准

- 至少完成 MQTT 的 planning-vs-gold diff；
- 至少完成 P+GoldDependency 的 oracle 或静态替换分析；
- 能判断主要问题更接近 specs 结构过重、planning 语义不足，还是 lowering/validator 缺陷；
- 已更新 `任务进度.md`。

# Step 5：Specs Optimization Decision Report

## 目标

基于 Step 1-4 的证据，形成最终决策报告，回答：

1. 当前是否有必要修改 specs 本身结构；
2. 如果要修改，是压缩 strict specs，还是保留结构但修 compiler/validator；
3. 哪些字段应该进入 strict specs；
4. 哪些字段应该进入 sidecar；
5. 哪些 planning stages 应优先优化；
6. 后续具体改造应拆成哪些实施任务。

## 决策类型

最终结论必须落入以下三类之一，或给出组合方案：

### Option 1：保留当前 specs 结构，优先修 validator/lowering

适用条件：

- Gold-Full 明显优于简化版本；
- 删除 behavior/wire/calls 后 coder 成功率或 header/compile/smoke 明显下降；
- P+GoldDependency 成功或显著改善；
- planning 语义覆盖尚可，主要失败在 dependency/header/system type/final validation。

可能后续任务：

```text
1. 禁止 dependency fallback 清空依赖；
2. 拆分 header_public_deps/source_call_deps；
3. 完整 public type dependency lowering；
4. 建立 system type registry；
5. final readiness 启用 rendered header validation；
6. dummy translation unit 编译所有 headers。
```

### Option 2：压缩 coder-facing strict specs，保留 planning sidecar

适用条件：

- Gold-Min-Interface 与 Gold-Full 成功率接近；
- 多个高细节字段不被 coder 消费；
- 删除 behavior/wire/calls/test vectors 不影响 build/smoke；
- 高细节字段主要增加 planning 失败率和 dependency 噪声。

可能后续任务：

```text
1. strict specs 只保留 coder 必需字段；
2. calls/wire/traceability/test vectors 下沉到 sidecar；
3. validator 从 sidecar 检查 planning 完整性；
4. coder prompt 只读取稳定字段；
5. specs compiler 根据 target profile 输出不同 density。
```

### Option 3：分层 + density profile

适用条件：

- 一部分字段对 validator/traceability 有价值，但 coder 不需要直接消费；
- 不同协议对细节需求不同；
- strict specs 可以保持较小，但 planning internal IR 仍需丰富。

可能后续任务：

```text
1. planning internal IR 保持 rich；
2. coder strict specs 保持 minimal-stable；
3. sidecar 保存 behavior/wire/calls/traceability；
4. target_profile 增加 specs_density = minimal/standard/rich；
5. compiler 根据 density lower 不同视图。
```

## 输出产物

```text
docs/specs_optimization/05_specs_optimization_decision_report.md
```

报告必须包含：

```text
1. Executive Summary
2. Evidence Summary from Step 1-4
3. Decision Criteria
4. Final Decision
5. Field Placement Recommendation
6. Stage Optimization Priority
7. Proposed Implementation Tasks
8. Risks and Open Assumptions
```

必须包含表格：

```text
| field/category | keep in strict specs? | move to sidecar? | validator-only? | rationale | evidence |
```

以及：

```text
| priority | target stage/module | issue | recommended action | expected benefit | risk |
```

## 完成标准

- 明确回答是否需要优化 specs 结构；
- 明确回答应该优化哪些 specs 字段；
- 明确回答应该优化哪些 planning stages；
- 形成后续 implementation tasks；
- 已更新 `任务进度.md`，并将大任务状态标记为完成或等待实现阶段。
