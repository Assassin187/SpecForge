**RQ2：编码前跨视图契约校验的有效性**

日期：2026-10-11。状态：实验设计，尚未运行；主表示例中的所有结果均为占位符。本文采用机制消融作为新 RQ2，原 S1–S4 或 G/P 格式比较的结果不能直接填入本主表。

**核心故事。** RFC 给出了协议应有的行为，SpecForge 需要自主决定模块、文件、函数和公共接口。这些决定分散在不同规格与实际 C 头文件中，可能互相矛盾。例如，已有 CoAP 记录中，类型规格要求 `coap_request_options` 包含 `payload`，实际头文件却没有该成员。头文件自身可以符合 C 语法，按规格生成的实现仍会失败。跨视图契约校验通过工程关系检查和由规格生成的 C 编译探针，在业务代码生成前发现并反馈这些矛盾。

> **RQ2：在相同自动规格草稿、修订机会和下游代码生成设置下，编码前的跨视图契约校验，能否减少跨模块集成错误，并降低完成实现的总成本？**

RQ1 评价完整规划流程的价值；RQ2 隔离其中的检查机制。这里的契约主要指符号、字段、类型、签名、依赖和归属等可机械检查的工程约束。实验不据此宣称完整 RFC 合规，也不宣称已证明状态机、所有权或协议算法的语义正确性。

**对照只改变编码前的检查与反馈。** 三组保留相同规格格式、协议内容、模型、LLM 自查与语义审阅，不裁剪协议字段或算法。

| 配置 | 编码前的检查 | 比较目的 |
|---|---|---|
| V0：普通规划与自查 | 基本格式、可加载性和共同任务约束；LLM 自查 | 检查机制的总体参照 |
| V1：头文件编译检查 | V0 + 公共头文件单独及共同编译 | 普通编译检查的增量 |
| V2：跨视图契约校验 | V1 + 工程关系检查、规格与头文件之间的类型/字段/签名探针 | 跨视图检查的额外价值 |

**主要比较预先设为 V2−V1，V2−V0 为次要比较。** V2 的工程检查包括模块/文件归属、公共符号唯一归属、依赖与函数引用解析，以及声明一致性。三组均保留正常自主工具使用；若 V0/V1 自行执行了等价检查，须记录，不能禁止正常自查来削弱对照。当前 G 分支已有部分编译检查，不能直接充当 V0。

**执行采用共同草稿的配对设计。** 一个预先登记的独立草稿生成尝试及其三组分支构成一个运行块。

1. 冻结任务、协议事实、需求、独立验收测试和代码版本；从共同输入生成完整自动草稿。此阶段只强制共同基本检查，不强制待消融的机械检查。
2. 在编码和目标机械检查之前保存草稿，记录内容哈希。草稿须包含全部规划规格及公共头文件；不使用人工 gold、已通过完整检查的发布包或吸收过 Coder 反馈的修订版。若共同阶段未生成完整草稿，三组均记失败并计入共同成本，不补选成功草稿。
3. 将同一草稿复制给 V0/V1/V2，以随机顺序运行分支。三组获得相同的固定自查/修订轮次与响应上限；使用相同修订指令，仅检查诊断不同。未用满预算可以结束本轮，实际消耗照实记录。
4. 每轮由对应检查器反馈诊断，Planner 可修改规格和头文件。最后分别按各组检查策略验收；预算内未通过的分支记为失败，不无限修订或挑选替代草稿。
5. 发布后，三组公共头文件均对 Coder 冻结。使用相同 Coder、开发构建、自测、额外修复和规格问题反馈流程。若触发编码后的规格修订，三组统一采用完整检查，保留相同修订机会。
6. 保存初始 Coder 任务结束的快照与最终快照，运行同一独立验收。独立验收结果不反馈给生成或修复阶段。

“初始代码”统一指初始 Coder 任务结束、额外修复任务开始之前的产物；该任务内部允许编译与修正，因此不能称为未经反馈的第一版代码。发布和加载层仅执行各组明确允许的检查，不能隐含重新开启已关闭的编码前检查。

**主表观察下游收益和完整成本。** 所有尝试都计入分母，包含检查未通过、未产出代码、超限和控制器错误。

| 主表指标 | 统一定义 |
|---|---|
| Code ↑ | 初始 Coder 任务结束时形成完整、可尝试构建的项目数 / 全部尝试数；允许编译失败 |
| Build₀ ↑ | 初始 Coder 任务结束时构建通过的项目数 / 全部尝试数 |
| Defects ↓ | 初始完整代码项目中的跨模块根因缺陷数，按项目取均值；无完整代码时记 NA，不记 0 |
| Accept ↑ | 有界修复后通过全部冻结独立验收场景的项目数 / 全部尝试数 |
| Tokens (M) ↓ | 每次尝试的总输入与输出 token，单位百万；包含共同规划、分支检查修订、编码和全部修复 |

根因缺陷聚焦类型/字段、接口签名、跨文件可见性、依赖及符号归属等集成问题。相同根因产生的重复或级联诊断合并；普通局部语法错误单列，规划中途尚未写完文件的提示不计为完整设计缺陷。对规格与初始代码作独立人工审计，保留证据和复核记录，不用目标检查器的通过标志直接定义真值。

代码缺陷均值是有完整代码产物时的条件统计，必须结合 Code、Build₀ 和 Accept 解读，不能通过减少交付来获得更低缺陷数。总成本包含失败尝试；复用草稿的共同规划成本全额计入每组，不除以三。补充材料报告总耗时、规划/编码/修复的成本分解、额外修复任务数、修改文件数及失败原因。若全部验收通过率出现天花板，可补充场景通过率，未运行的场景按失败计。

**补充实验解释检查机制为何起效。** 对共同草稿独立标注自然存在的工程矛盾，比较三组的检出、遗漏和错误拒绝，跟踪“诊断—规格修正—下游缺陷”的对应关系。已有 CoAP `payload` 案例可用于说明，主结论依赖多个自然生成样本。少量受控错误与合法替代设计仅用于覆盖面验证，与自然错误分开报告。

如进一步主张“前置检查优于后置检查”，再增加 Vlate：只做 V1 的编码前检查，在初始代码任务结束后强制执行同一完整检查，并在相同总修订预算内继续。该组默认不纳入主实验；三组主实验不能单独证明最优检查时机。

默认试跑为 4 协议 × 2 独立草稿生成尝试 × 3 组 × 1 Coder 回放，共 8 个配对块、24 个评估尝试，最多启动 24 次代码生成；正式重复规模依据试跑的缺陷频率、变异和成本确定，之后冻结。以独立草稿生成尝试为配对单位，Coder 回放属于块内重复；协议场景、重复诊断和 sanitizer 执行不算独立样本。预先区分基础设施错误与方法失败，保留全部记录；重试及费用按三组相同规则处理。

- V2 相比 V1 减少集成缺陷，并降低总成本或提高同预算下完成率：支持独立方法贡献。
- 缺陷减少但总成本上升：报告可靠性与成本的取舍；若协议通过率持平，仍可讨论工程收益。
- 仅检查器通过率变高，或仅人为错误上有效，而自然样本的下游收益不足：不能据此宣称独立技术贡献成立。
